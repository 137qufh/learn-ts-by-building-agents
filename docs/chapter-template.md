# 章节约定（Chapter Template）

每一章都遵循同一套结构。这样读者换章节时不需要重新适应，贡献者也知道东西该放哪里。

## 目录结构

以第 1 章为例（`NN` 是两位数章节号，`slug` 是英文短名）：

```
chapters/01-basics/
  README.md                 本章入口：目标、前置知识、课程目录、项目、自测清单
  01-xxx.md ... 0N-xxx.md   一节一个文件，按学习顺序编号
  examples/
    01-xxx.ts               与同编号课程配套的可运行示例
  project/                  （可选）章末项目的说明和运行入口
exercises/01-basics/
  01-xxx.ts                 练习题：签名写好，函数体是 todo()
  01-xxx.test.ts            测试即规格：没做完时失败，做对了变绿
  01-xxx.test-d.ts          （可选）类型测试：检查类型是否正确，由 tsc 检查而不是运行
  project/                  章末项目的题目和测试
solutions/01-basics/
  01-xxx.ts                 参考答案（与题目导出完全相同的名字）
  project/
```

## 每个文件该写什么

### 章节 README.md

1. 一句话说清这一章解决什么问题
2. **学完你能**：3–6 条可检验的能力（"能写出……"，而不是"了解……"）
3. **前置知识**：需要先读哪些章节
4. **课程目录**：表格，每节一行，附对应的示例和练习
5. **章末项目**：做什么、为什么和 agent 有关
6. **自测清单**：读者合上书能回答的问题
7. 下一章链接

### 课程（`0N-xxx.md`）

- 开头一句"这一节要解决的问题"，而不是定义
- 先给能跑的代码，再解释为什么
- 每个概念都回答"为什么 TS 要这样设计 / 什么时候用"
- 会报错的写法用 `// @ts-expect-error` 标出来，并写上原因
- 只在真正有帮助时和 Python / JavaScript 对比，一句话即可
- 结尾是 **小结**（3–5 条要点）和 **练习** 链接

### 示例（`examples/*.ts`）

- 每个文件都能用 `node 文件名.ts` 或 `pnpm tsx 文件名.ts` 直接运行，CI 会逐个运行检查
- 用 `console.log` 打印能说明问题的结果，注释里写出预期输出
- 演示类型错误时必须用 `// @ts-expect-error`：如果哪天那行不再报错，`tsc` 会失败，说明讲解过时了
- 标了 `@ts-expect-error` 的代码在运行时照样会执行。如果错误示范会产生副作用（修改数据、抛错、打印），把它放进一个从不调用的函数里

### 练习（`exercises/`）

- 文件顶部注释：题目描述、对应课程链接、运行命令
- 类型和函数签名由题目给出，函数体调用 `todo()`（返回 `never`，运行时抛错）
- 测试用中文描述行为，测试本身就是规格说明；边界情况要覆盖到
- 练习文件必须能通过 `tsc`（即使还没实现），这样读者的编辑器里不会一开始就一片红
- 测试文件的顶层和 `describe` 的回调里不要调用题目里的函数（它们还会抛出 TODO）：放进 `test` 里，或者包成一个辅助函数在 `test` 里调用。否则整个文件加载失败，读者看不到任何一条具体的测试

### 异步练习（从第 3 章开始）

- 测试不能依赖网络或 API key。需要 HTTP 的地方，注入一个假的 `fetch`（参考 `chapters/03-async/project/fake-openai.ts`），或者在 `127.0.0.1` 上临时启动一个 `node:http` 服务器
- 时钟、随机数、`sleep` 作为可选参数传入，测试里换成确定的版本；只有测试取消、超时这类行为时才用真实的短定时器（几毫秒到几十毫秒），并给断言留出足够的余量，避免在慢机器上偶尔失败
- 清理也要测：监听器有没有移除（`vi.spyOn`）、定时器有没有清除（`process.getActiveResourcesInfo()`）、上游的 `finally` 有没有执行
- 写完一个"抓 bug"的测试后，故意把答案改错一次，确认测试真的会失败
- 测试导入的辅助代码放在 `chapters/<章>/project/` 下；`tests/type-exercises.test.ts` 会把 `chapters/` 一并复制，保证它们对参考答案也能通过 `tsc`

### 类型练习（`*.test-d.ts`，从第 2 章开始）

有些练习考的是类型本身：写对一个泛型签名、一个映射类型。这类练习配一个类型测试文件：

- 用 Vitest 的 `expectTypeOf` 写断言；`pnpm ex` 会用 `tsc` 检查它，类型不对就算测试失败
- 还没实现的类型写成 `Todo`（从 `exercises/todo.ts` 导入）；需要学习者自己写签名的函数，先用 `any` 占位，
  保证同目录的运行时测试在没做完时也能通过 `tsc`
- 根目录的 `tsconfig.json` 排除了 `exercises/**/*.test-d.ts`（它们在做完之前一定报错），
  `exercises/tsconfig.json` 把它们包含回来，供编辑器和 `pnpm ex` 使用；`pnpm ex:types` 可以看到 `tsc` 的完整输出
- 参考答案由 `tests/type-exercises.test.ts` 检查：它把答案放到练习文件的位置，再对类型测试和运行时测试运行 `tsc`

### 参考答案（`solutions/`）

- 与题目导出完全相同的名字（`tests/exercises.test.ts` 会检查）
- 在关键处写注释解释"为什么这样写"，必要时给出另一种写法

## 质量门槛

提交前本地运行：

```bash
pnpm check   # = typecheck + format:check + test
```

- 所有示例、答案、测试都必须通过 `tsc` 和 `vitest`
- 讲解中的每个说法都应该能被代码验证；不确定的说法宁可不写
- 用当前版本的 TypeScript（本仓库使用 TypeScript 7）的写法和默认值
