# 3.1 事件循环：JavaScript 怎么"同时"做很多事

> 这一节要解决的问题：agent 要等模型回复、等工具执行、等用户输入，每一次等待都可能长达几秒。JavaScript 只有一个线程，它是怎么在等待的同时继续干别的事的？代码到底按什么顺序执行？

示例代码：[examples/01-event-loop.ts](examples/01-event-loop.ts)

这一章开始，代码不再是"从上到下一行行执行完"那么简单了。在学 `Promise` 和 `async`/`await` 之前，先花一节建立正确的心智模型。后面几乎所有"为什么会这样"的问题，答案都在这里。

## 单线程，但不阻塞

JavaScript 代码运行在 **一个线程** 上：同一时刻只有一段 JS 代码在执行。可是一个 agent 明明可以一边等模型的流式输出，一边响应用户按下的 Ctrl+C，这是怎么做到的？

答案是：**等待不是由 JS 线程来做的。** 发起一个网络请求时，JS 只是把请求交给 Node.js 的底层（操作系统的网络接口、线程池），然后立刻继续执行后面的代码。等数据到了，底层把"数据到了，请执行这个回调"这件事放进一个 **队列**。JS 线程手头的代码执行完以后，就去队列里取下一件事来做。

这个"执行完当前代码 → 取下一个任务 → 执行 → 再取下一个"的循环，就是 **事件循环**（event loop）。

```
  ┌──────────────────────────┐
  │ 执行一段同步代码（直到完） │
  └────────────┬─────────────┘
               ▼
  ┌──────────────────────────┐
  │ 清空微任务队列             │  ← Promise 的回调在这里
  └────────────┬─────────────┘
               ▼
  ┌──────────────────────────┐
  │ 从任务队列取下一个任务      │  ← 定时器、网络数据、文件读完……
  └────────────┬─────────────┘
               └──────► 回到第一步
```

和 Python 的 `asyncio` 很像：一个线程、一个循环、遇到等待就让出。区别是在 JavaScript 里，事件循环是语言运行时自带的，你从来不需要自己启动它。

## 两种队列：任务和微任务

先看一段代码，猜猜输出顺序：

```ts
console.log("1 同步：开始");

setTimeout(() => {
  console.log("5 定时器（宏任务）");
}, 0);

Promise.resolve().then(() => {
  console.log("3 Promise 回调（微任务）");
});

queueMicrotask(() => {
  console.log("4 queueMicrotask（微任务）");
});

console.log("2 同步：结束");
```

输出是 1、2、3、4、5。规则只有三条：

1. **同步代码一口气执行完**，中途不会被任何回调打断。所以 1 和 2 最先输出
2. 当前代码执行完后，**先清空微任务队列**（microtask queue）。`Promise` 的回调（`.then`）和 `queueMicrotask` 都是微任务，所以接着是 3 和 4
3. 微任务清空后，才从 **任务队列**（task queue，也常叫"宏任务"）里取一个任务执行。`setTimeout` 的回调是任务，所以 5 最后输出，哪怕它的延迟是 0

`setTimeout(fn, 0)` 的意思不是"立刻执行"，而是"至少 0 毫秒后，把 `fn` 放进任务队列"。它要排在当前同步代码和所有微任务后面。

### 微任务会"插队"到底

微任务执行的过程中如果又产生了新的微任务，新的微任务也会在这一轮被执行完，然后才轮到下一个任务：

```ts
setTimeout(() => console.log("c 定时器"), 0);
Promise.resolve()
  .then(() => console.log("a 微任务"))
  .then(() => console.log("b 微任务里产生的微任务"));
// a → b → c
```

`a` 的回调执行完，`.then` 链上的下一个回调才被放进微任务队列，它仍然排在定时器前面。这也意味着一个不停产生微任务的循环会让定时器、网络回调永远得不到执行，这种情况很少见，知道有这回事即可。

> Node.js 还有 `process.nextTick` 和 `setImmediate` 两个特有的调度方式，它们的执行时机有更细的规则。本课程不会用到它们，写跨平台的代码时也应该优先用 `Promise` 和 `queueMicrotask`。

## 不要阻塞事件循环

规则 1 的反面是：**一段同步代码执行多久，其他所有事情就等多久。**

```ts
const scheduledAt = Date.now();
setTimeout(() => {
  console.log(`实际等了 ${Date.now() - scheduledAt}ms`); // 100 多，而不是 10
}, 10);

const start = Date.now();
while (Date.now() - start < 100) {
  // 一段耗时 100ms 的同步计算
}
```

定时器早就"到点"了，但 JS 线程被 `while` 循环占着，回调只能在队列里干等。

对 agent 来说，这意味着：

- 网络请求、读写文件、等待子进程，**都要用异步的 API**（`fetch`、`fs/promises`），不要用 `readFileSync` 这类同步版本去等待慢操作（启动时读一次配置文件这种情况除外）
- 一大段 CPU 密集的计算（比如在本地对很长的文本做分词统计）会让整个 agent 卡住：期间流式输出停住、Ctrl+C 没反应。这类工作要么拆成小段，要么放到 `worker_threads` 里
- 反过来，**只要不阻塞，一个线程就能同时管理成百上千个正在进行的请求**。3.5 节会利用这一点并发地执行工具调用

## 这和类型有什么关系

事件循环是运行时的行为，TypeScript 的类型系统不会描述"这段代码什么时候执行"。但下一节会看到，`Promise<T>` 这个类型把"一个将来才会有的值"变成了可以传递、组合、检查的东西，类型系统从那里开始帮上忙。

## 小结

- JS 只有一个线程，但等待由运行时在后台完成；结果就绪后，回调被放进队列，由事件循环依次执行
- 顺序规则：同步代码一口气执行完 → 清空所有微任务（`Promise` 回调、`queueMicrotask`）→ 执行一个任务（定时器、I/O 回调）→ 重复
- `setTimeout(fn, 0)` 不是立刻执行，而是排到当前代码和所有微任务之后
- 长时间的同步代码会阻塞一切：慢操作用异步 API，CPU 密集的工作拆开或放进 worker
