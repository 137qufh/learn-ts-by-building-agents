# 6.5 停止条件与错误恢复

> 这一节要解决的问题：模型说"我说完了"是循环唯一的正常出口吗？输出被截断、被内容过滤拦下、一遍遍发出同样的调用、网络在流到一半时断开、用户按了 Ctrl+C……每一种情况，循环该怎么结束？结束之后，聊天记录还能接着用吗？

示例代码：[examples/05-stop-and-recover.ts](examples/05-stop-and-recover.ts)

## 停止的原因是一个可辨识联合

6.1 节的循环只有两种结局："完成"和"达到步数上限"。真实的 harness 有更多种，而且调用方需要区分它们：完成了就显示回答，被截断了也许要提示用户"回答不完整"，出错了要显示错误。用 [1.6 节](../01-basics/06-unions-and-narrowing.md)的可辨识联合描述：

```ts
type StopReason =
  | { type: "completed" }
  | { type: "max_steps"; maxSteps: number }
  | { type: "length" }
  | { type: "model_stopped"; finishReason: string }
  | { type: "repeated_tool_calls"; name: string; times: number }
  | { type: "cancelled" }
  | { type: "error"; error: Error }
  | { type: "stopped_by_middleware"; middleware: string; reason: string };
```

每种原因带着自己需要的信息：错误带着 `error`，重复带着是哪个工具、几次。调用方 `switch (stopReason.type)` 之后就能拿到它们，而且加了新的原因时，没有处理它的 `switch` 会被 `never` 检查发现（[1.7 节](../01-basics/07-any-unknown-never.md)）。

harness 的 `run()` **永远不抛出**：所有结局都是一个 `StopReason`，连同完整的聊天记录一起交出去。出错了也要把记录交出去：前面九步的工作不应该因为第十步的网络错误就全部丢掉。

## 读懂 finish_reason

每个回合结束时，模型给出一个结束原因。harness 根据它和"有没有工具调用"决定下一步：

| finish_reason     | 有工具调用         | 没有工具调用       |
| ----------------- | ------------------ | ------------------ |
| `tool_calls`      | 执行工具           | 模型停下了（异常） |
| `stop`            | 执行工具           | **完成**           |
| `length`          | **停下：被截断了** | 停下：被截断了     |
| `content_filter`  | 停下：被拦下了     | 停下：被拦下了     |
| 没有（`unknown`） | 执行工具           | 完成               |
| 其他新的值        | 执行工具           | 模型停下了         |

几个值得注意的地方：

- **以"有没有工具调用"为准，而不是只看 `tool_calls`**。有些兼容接口在有工具调用时给的是 `stop`，有的干脆不给结束原因。[5.6 节](../05-validation/06-api-responses.md)说过：对 API 的变化要宽容
- **`length` 时不执行工具**，哪怕有工具调用。输出被截断时，最后一个工具调用的参数很可能是半截 JSON；就算能解析，也不能确定模型本来想写的就是这些。被截断的文字留在记录里，由调用方决定要不要让模型继续
- 不认识的新值不会让 harness 崩溃，而是如实报告 `model_stopped`

## 发现重复

模型有时会陷入循环：读同一个文件，得到同样的内容，再读一遍。`maxSteps` 最终会停下它，但在那之前已经浪费了很多步。更早的办法是 **发现重复**：同样的一批调用连续出现 3 次，就停下。

"同样"要小心定义。`{"path":"a.ts"}` 和 `{ "path": "a.ts" }` 是同一个调用，`{"a":1,"b":2}` 和 `{"b":2,"a":1}` 也是。所以先解析参数，再用 **键排好序** 的方式重新序列化：

```ts
stableStringify({ b: 2, a: { d: 1, c: 0 } }); // '{"a":{"c":0,"d":1},"b":2}'
```

`JSON.stringify` 按对象创建时的键顺序输出，模型生成的参数顺序不固定，所以不能直接比较原文。调用的 `id` 每次都不一样，也不参与比较。

发现重复后，最后这批调用 **不执行**，每个调用补上一条结果，写明为什么没有执行。和取消一样，记录必须是合法的。

## 修复聊天记录

无论因为什么停下，交出去的记录都要满足接口的规则：**每个工具调用都有一条结果，每条结果都对应一个调用**。违反它的后果是下一次请求直接被拒绝：

```text
400 An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'.
```

在正常的流程里，harness 会给每个调用一个结果（包括超时和取消，6.3 节）。但总有意料之外的路径：中间件抛出了异常、`length` 时没有执行的调用……与其在每条路径上都小心翼翼，不如在出口统一检查一遍。这就是 `repairHistory`：

- 缺少结果的调用，补上一条"没有结果"的说明
- 找不到对应调用的结果（比如重复的结果），丢掉

[第 1 章的项目](../01-basics/09-project-chat-transcript.md)写过"找出还没有结果的工具调用"，现在它派上了用场。这是一种常见的防御性设计：**在边界上统一保证不变量**，而不是相信内部的每一条路径都做对了。

## 中断时保留什么

用户在模型输出到一半时按下 Ctrl+C。[3.10 节](../03-async/10-project-streaming-client.md)的思考题问过：这一半的文字应该保留在聊天记录里吗？

这一章的回答是 **保留**。用户已经看到了这些文字，接下来他说的话很可能就是针对它们的（"不对，不是这个意思"）。如果记录里没有它，模型就不知道用户在说什么。没有收到完整的工具调用（它们在流的最后才拼好）就不保留，所以这条 assistant 消息只有文字，不会留下没有结果的调用。

## 错误恢复：重试，但只在一层重试

模型的流在中途断开了：空闲超时、连接被重置、服务器发来半截数据。这一步可以整个重来：丢掉收到的半截内容，重新发同样的请求。harness 发出一个 `step_retry` 事件，界面看到它就知道要清掉这一步已经显示的文字（下一节）。

但有两种错误不应该在这一层重试：

- **取消**：用户要停，就停
- **`ApiError`**：它来自建立连接的阶段，客户端已经按自己的策略重试过了（[3.7 节](../03-async/07-retries.md)）

第二条值得多说一句。假设客户端对 503 重试 3 次，harness 又对整步重试 3 次，一次故障就会变成 4 × 4 = 16 个请求。如果再外面还有一层（比如调用 agent 的服务也会重试），就是 64 个。这叫 **重试放大**（retry amplification），在服务出故障时，正是这些成倍增加的重试把它彻底压垮。规则很简单：**同一种错误只在一层重试**。客户端负责连接阶段的错误，harness 只负责客户端不管的流中途的错误。

## 小结

- 停止原因是一个可辨识联合；`run()` 永远不抛出，任何结局都带着完整的记录
- 以"有没有工具调用"为主判断是否继续；`length` 时不执行工具；不认识的结束原因如实报告
- 用键排序的序列化比较调用，连续重复就停下
- 在出口统一修复记录：每个调用一个结果，每个结果对应一个调用
- 中断时保留用户已经看到的文字
- 流中途的错误整步重试；取消和客户端已经重试过的 `ApiError` 不重试，同一种错误只在一层重试
