# 6.4 上下文管理：token 预算与截断

> 这一节要解决的问题：agent 每走一步，聊天记录就长一截：一个 `read_file` 可能带回几千行代码。模型的上下文窗口是有限的，超出了请求直接失败；就算没超出，记录越长越贵、越慢，模型也越容易"走神"。harness 怎么控制发给模型的内容？

示例代码：[examples/04-context-window.ts](examples/04-context-window.ts)

## 记录和窗口是两回事

先分清两个概念：

- **聊天记录**（history）：发生过的一切，完整保存，只追加。它是给人看的、给下一轮对话用的、出了问题时排查用的
- **上下文窗口**（window）：这一次请求 **实际发给模型** 的内容，是从记录里挑出来的

这一节所有的"省略"和"截断"，作用的都是窗口，不改动记录本身（工具输出的截断是例外，见下文）。harness 每一步都从完整的记录重新计算窗口，所以策略可以随时调整，什么都不会真的丢掉。

## 估算 token

上下文的长度按 token 计算。准确的数字只有模型的分词器（tokenizer）知道，不同的模型还不一样。harness 需要的是一个 **便宜、偏保守** 的估算：

```ts
estimateTokens("Hello, world"); // 3：英文大约 4 个字符一个 token
estimateTokens("你好世界"); //       4：汉字大约一个字一个 token
```

常用的经验值：英文和代码大约 4 个字符一个 token；中文、日文、韩文大约一个字一个 token（新一些的分词器会更省，按 1 算是偏保守的）。练习里用 Unicode 属性转义区分这两类字符：

```ts
const WIDE = /[\p{Script=Han}\p{Script=Hiragana}\p{Script=Katakana}\p{Script=Hangul}]/u;
```

`\p{Script=Han}` 匹配所有汉字，`u` 标志让正则按 **码点** 而不是 UTF-16 单元工作；`for...of` 遍历字符串也是按码点的，一个 emoji 就是一个字符，不会被拆成两半。

每条消息再加一个固定开销（角色、分隔符），工具调用的名字和参数也要算进去：它们同样占用上下文。

> 估算总会有误差。更精确的做法是用模型返回的真实用量校准：上一次请求的 `usage.inputTokens` 就是上一个窗口的准确长度，和估算值一比，就知道估算偏了多少。这一章的 harness 只用估算，留给你作为改进的方向。

## 截断工具的输出

最大的一块往往是工具的输出。一次 `read_file` 读到一个生成出来的大文件，一次 `search` 匹配到上千行，一个测试命令打印了满屏日志。工具的输出要在 **进入记录之前** 就截断：

```ts
truncateMiddle(output, 20_000);
// 开头一万个字符 + "\n…（中间省略了 48213 个字符）…\n" + 结尾一万个字符
```

为什么保留开头和结尾、省略中间？想一想命令行输出：开头是在做什么，结尾是最终结果和报错信息，中间往往是重复的进度和日志。还要明确告诉模型"这里省略了"，否则模型会以为看到的就是全部，基于不完整的信息下结论。

这是唯一一处修改了记录本身的地方：完整的输出太大，留在记录里没有意义（真需要的话，可以把它写进文件，记录里放路径）。

## 省略较早的消息

记录总长超出预算时，从 **最早的** 消息开始省略。但不是一条一条地删，有三条规则：

**1. 开头的 system 消息永远保留。** 它是 agent 的"角色设定"和规则，删掉它 agent 就变了一个人。

**2. 工具调用和它的结果一起删。** 只删掉 assistant 那条带 `tool_calls` 的消息，留下它的 `tool` 结果，接口会拒绝请求：tool 消息必须紧跟在调用它的那条消息后面。反过来也一样。所以先把消息分成"不能拆开"的组：

```text
[user]  [assistant + tool_calls, tool, tool]  [assistant]  [user]  ...
```

**3. 最后一组永远保留。** 哪怕它自己就超出了预算：没有最近的消息，模型根本不知道现在要做什么。这时请求可能会失败，但那是一个应该被看见的错误（预算设得太小，或者某个工具输出没有截断），而不是悄悄地发一个空请求。

省略之后，在 system 消息后面插入一条说明：

```text
（为了控制上下文长度，更早的 12 条消息已经省略）
```

和截断工具输出一样：**让模型知道信息不完整**。它看到这条说明，就不会对"之前说过什么"过于自信，需要时会重新读文件。说明本身也占预算，计算时要算进去。

> 说明用的是 system 消息。OpenAI 的接口允许 system 消息出现在中间；如果你用的服务商不允许，可以改成一条 user 消息，或者把它拼进开头的 system 消息里。

## 更聪明的策略

"删掉最早的"是最简单、最可预测的策略，但不是唯一的：

- **摘要**（compaction）：用模型把较早的对话总结成一段话，替换掉原文。保留了更多信息，代价是一次额外的模型调用，以及摘要可能丢掉关键细节。很多编程 agent 在上下文快满时都会这样做
- **按重要性保留**：比如永远保留用户的第一条消息（原始任务）
- **把大块内容放在外面**：工具的输出写进文件，记录里只放摘要和路径，需要时再读

它们都可以在 `fitToBudget` 的位置替换进来。harness 的结构让这件事很容易：窗口是每一步重新计算的，策略只是一个函数。

## 小结

- 记录是完整的历史，窗口是每次发给模型的子集；省略作用于窗口
- token 用"英文 4 个字符、中日韩 1 个字"估算，按码点遍历；工具调用也要计算
- 工具输出在进入记录前截断，保留开头和结尾，并写明省略了多少
- 省略较早的消息时：system 消息保留、工具调用和结果整组删除、最后一组保留，并插入说明
- 永远让模型知道"这里的信息不完整"
