# 7.7 检索：关键词和本地向量

> 这一节要解决的问题：笔记多了以后，不能把全部塞进提示。关键词对"牛奶"很够用，对"乳制品"就不够。向量检索通常要一个 embedding 模型，这一章又不能联网。接口该怎么留？

示例代码：[examples/07-retrieval.ts](examples/07-retrieval.ts)

## 为什么是两路，而不是只留一路

上一节的 `search` 按片段重叠计数，适合"库还小、查询就是原文里的词"。重叠数是整数，两条文档只要都含"牛奶"就并列，正文长的和正文刚好就是这个词的分不出来，也不认识同义词。

向量把一段文本变成一个等长的数组。两段近，其余弦接近 1；正交是 0；方向相反接近 -1。只靠向量会丢掉"这个词到底出现了没有"：哈希向量（下面）对词的有无敏感，对同义词不敏感；真正的 embedding 模型反过来，有时会把一个没出现的近义词排得很靠前。两路一起用，是承认每路都有盲区。

分数各占一半：

```ts
const keyword = 命中的查询片段数 / 查询片段数; // 查询没有片段时是 0
const vector = (cosine(query, doc) + 1) / 2; // 从 [-1, 1] 收到 [0, 1]
score = 0.5 * keyword + 0.5 * vector;
```

余弦先平移，两路才在同一个区间里，一半一半才有意义。不平移的话，余弦是 -1 的文档会把关键词的 1 拉成 0。

空向量的余弦规定为 0，而不是 `NaN`。空文本嵌入之后全是 0，长度是 0，点积除以长度会得到 `NaN`，排序时 `NaN` 和谁比都是 false，顺序就不确定了。长度不同是调用错误，抛出去：那是两套维度混用了，不是"有点不像"。

## 不联网的向量是怎么算的

真正的 embedding 模型把"牛奶"和"乳制品"放在附近。那需要一次模型调用，和"练习、评测都能离线跑"冲突。默认实现用哈希，四步：

1. 用和 7.6 节相同的片段（词，加上长词的二字）
2. FNV-1a 把片段散到固定个桶里。默认 32。`dimensions` 不是正整数就抛
3. 哈希的最低位决定这个桶加 1 还是减 1。两个不相干的词落进同一个桶时，有机会互相抵消，而不是只会越加越大
4. 除以向量的长度（L2）。不归一化的话，长文档每个桶的数字都更大，余弦会被长度支配，而不是被"有哪些词"支配

同样的文本永远得到同样的向量，没有随机数，也没有网络。示例打印：

```text
same true
closer true
orthogonal true
```

"牛奶"和自己的余弦是 1。带上二字片段之后，"牛奶盒"和"牛奶"比"牛奶"和"量子"更近。空文本的余弦是 0。练习把 8 维的"牛奶"锁成 `[0, 0, 0, 0, 1, 0, 0, 0]`：一个片段、一个桶、符号是正的、归一化之后就是 1。改了哈希或者忘了归一化，这个向量对不上。

## 假的嵌入把公式钉死

练习注入的嵌入是：文本里有 `alpha` 就返回 `[1, 0]`，有 `beta` 就返回 `[0, 1]`，否则 `[0, 0]`。查询 `alpha`：

- 文档 `alpha story`：关键词重叠是 1，余弦是 1，分数是 `0.5 * 1 + 0.5 * 1 = 1`
- 文档 `beta note`：关键词是 0，余弦是 0，向量项是 `(0 + 1) / 2 = 0.5`，分数是 `0.25`

所以 `beta` 仍会出现在 `limit` 够大的结果里，排在后面。0.25 是"余弦为 0"的底分，不是弱相关。把融合改成只用余弦，两条的顺序可能还在，但 1 和 0.25 对不上，测试会红。只用关键词的话，`beta` 的分数是 0，也不对。

8 维的 `牛奶` 被锁成 `[0, 0, 0, 0, 1, 0, 0, 0]`。一个片段落进下标 4 的桶，符号是正的，归一化之后长度是 1。忘了归一化，那个位置是 `1` 以外的数，或者旁边还有别的非零，都对不上。

## 它做不到什么

归一化之后，"cat" 和 "cat cat" 的方向一样。次数被抹掉了。如果"出现两次"本身是信号，这一路看不见，要靠关键词那一路，或者干脆不归一化并接受长文档占优。这里选择归一化，把这个限制写在明处。

同义词仍然看不见。"牛奶"和"乳制品"如果没有共同片段，就只靠碰巧落进同一个桶。桶只有 32 个的时候，不相干的词也会撞在一起。所以默认向量 **不是** embedding 模型的替代品。它证明的是接口：

```ts
interface Embedder {
  embed(text: string): readonly number[];
}
```

测试注入一个假的：含有 `alpha` 的文本得到 `[1, 0]`，含有 `beta` 的得到 `[0, 1]`。这样余弦是我们指定的，排序错了就能确定是融合公式错了，而不是哈希碰巧。真正要语义时，换成调用模型的 `embed`，`createRetriever` 的调用方不用改。换了模型之后分数会变，7.9 节的基线要一起换，不然会把"换了嵌入"误报成检索退步。

`add` 的 id 省略时是 `m1`、`m2`……显式 id 重复就抛。空文本抛。`search` 的 `limit` 默认 5，0 返回空数组，负数抛。没有"不相关就丢掉"：向量那一路给了每条一个底分，所以限量之前，不相干的文档也在列表里，只是排在后面。调用方用 `limit` 截断，而不是希望分数为 0 的自动消失。关键词那一路是 0、余弦也是 0 时，底分是 `0.5 * 0 + 0.5 * 0.5 = 0.25`。看到 0.25 不要以为它"有点相关"。

用装在仓库里的 `createLocalEmbedder(32)` 量过：`牛奶` 和 `乳制品` 的余弦是 0，和 `量子` 也是 0。默认向量没有把近义词拉近。`cat` 和 `cat cat` 的余弦是 1，次数确实被归一化抹掉了。这两句都是跑出来的数，不是比喻。换桶的个数或换哈希，练习里 8 维的那个单位向量会先红。

## 停下来想一想

1. 为什么余弦要先变成 `(cos + 1) / 2` 再和关键词平均？不平移时，一个完全反向的文档会把关键词的满分拉成多少？
2. 默认向量能把"牛奶盒"排在"量子"前面。它能把"乳制品"排在"量子"前面吗？什么时候必须换 `Embedder`？

`search` 不把低分文档丢掉，是因为底分几乎总是大于 0。调用方用 `limit` 决定要几条，默认 5。`limit` 为 0 返回空数组，负数抛 `RangeError`，和记忆那一节一样：0 是"我不要结果"，负数是调用错了。显式 id 重复也抛，空文本也抛。自动编号 `m1`、`m2` 和 `createMemoryStore` 的 id 不是同一个空间，两个库各数各的。工作室里的 `remember` 走的是检索这一个，不是记忆那一个：要的是按查询排序，不是把库按时间列出来。

维度要在构造时定死。查询向量和文档向量长度不同，`cosine` 抛错，而不是截断或补零。补零会让一个 8 维的嵌入和一个 32 维的嵌入"能比"，比出来的数没有意义。换 `Embedder` 的同时换 `dimensions`，旧文档要重新 `embed`，不能把旧向量留在库里。

查询没有片段（空字符串、只有标点）时，关键词项是 0，不是 `0/0`。空文本的向量是全 0，余弦按上面的规定是 0，于是空查询对一条正常文档的分数就是那个 0.25 的底分。不要在这一步抛"查询是空的"：记忆那一节的 `search("")` 返回空数组，检索这一节把空查询当成一个合法的向量。两个函数回答的问题不一样，空查询的约定也不必相同。

FNV-1a 不是加密，也不用选个别的哈希来"更随机"。要的是同一段文本每次得到同一个桶。换一个常数，8 维那个单位向量会挪到别的下标，练习先红，演示里的"更近"也不再有保证。常数写在实现里，不做成参数。

调用方要换哈希，就换整个 `Embedder`，不要给 `createLocalEmbedder` 再加一个 `algorithm` 选项。

## 小结

- 分数是关键词重叠和余弦各一半。余弦先收到 `[0, 1]`。空向量的余弦是 0，长度不同则抛
- 默认向量是 FNV-1a、带符号的桶、再 L2 归一化。离线、确定、没有同义词，次数也被归一化抹掉
- 8 维的"牛奶"是一个单位向量，锁在测试里
- `Embedder` 可以替换。假的嵌入用来测排序；真的模型用来做语义。换模型要换评测基线

排序在分数相同的时候按 id 的字典序，不按插入顺序。两条文档撞进了同样的桶、关键词也一样时，结果才稳定。不写这一级，测试偶尔过、换一次 Map 的实现又不过。
