# 7.8 评测：确定性用例

> 这一节要解决的问题：改了提示或换了检索，你怎么知道没有变差？看一次演示不够。评测要能在没有 API key 的时候失败得明明白白。

示例代码：[examples/08-evals.ts](examples/08-evals.ts)

## 先断言你能断言的

agent 的一次运行有三样可以检查，而且都不需要另一个模型：

- **最终文本**：等于某句，或包含某几段
- **工具序列**：调用了哪些工具，顺序对不对。`tools` 是完整序列；`toolsInclude` 只要求按顺序出现，中间可以夹别的
- **记录**：每一步的角色、文本、工具名。这是黄金轨迹，差一步就失败

这些断言抓的是 harness、工具和脚本化模型组成的程序：有没有调用不该调用的工具，失败之后有没有继续，文本里有没有必须出现的事实。它们抓不住"这段总结写得优不优雅"。那是下一节的事，而且不该拿来替代这里能写死的检查。

## 一个失败不要挡住后面的

`runEval` 跑完所有用例。一个用例抛错，记成 `运行抛出了错误：...`，继续下一个。示例的输出是先报"坏了"，再报"好的"，最后 `passed 1`。停在第一个失败上，你修一个就冒出一个，来回的次数变多，也看不到一次改动打坏了几条。

一条用例可以同时有多条原因：文本不对，并且工具序列也不对。原因里带上期望和实际，失败信息本身就是规格。记录对不上时说出是第几步（从 0 开始），而不是只说"不一样"。

用例的 `run` 由调用方提供。测试里它可以是一段固定的轨迹，也可以是 `createAgent` 加 `createScriptedModel` 跑出来的结果。评测函数不关心模型从哪来，只关心结果的形状。这样同一套断言既能锁住脚本，也能在你接上真正的模型时复用。真正的模型不稳定，断言就要放宽到"包含"而不是"等于"，并且准备好偶尔失败。那是下一节回归容忍度要处理的波动，不是这一节把断言写松。

## 小结

- 能用文本、工具序列、记录说清楚的，就不要交给另一个模型
- 全部用例都要跑完。抛错是这条用例的失败原因
- 失败信息里带期望和实际。评测函数不绑定某一种模型
