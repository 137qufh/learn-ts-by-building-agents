# 7.8 评测：确定性用例

> 这一节要解决的问题：改了提示、换了检索、调了 `maxSteps`，你怎么知道没有变差？看一次演示不够。评测要能在没有 API key 的时候失败得明明白白。

示例代码：[examples/08-evals.ts](examples/08-evals.ts)

## 先断言写得死的那部分

agent 的一次运行里，有三样不需要另一个模型就能检查：

| 断言                          | 问的问题                             | 什么时候用                       |
| ----------------------------- | ------------------------------------ | -------------------------------- |
| `textEquals` / `textIncludes` | 最终回答里有没有必须在的事实         | 数字、专有名词、"必须拒绝"这种话 |
| `tools`                       | 工具名的完整序列，顺序和次数都要一致 | 黄金路径：就该先搜再读           |
| `toolsInclude`                | 这些名字按顺序出现过，中间可以夹别的 | 只关心有没有漏掉关键的一步       |
| `transcript`                  | 每一步的角色、文本、工具名           | 整段轨迹都不能变                 |

`tools` 和 `toolsInclude` 不要混用。完整序列会在模型多叫了一次无害工具时失败，适合脚本化的假模型：轨迹是你写的，多一步就是回归。包含关系适合"至少要读过文件"，多出来的查看不该让用例红。空的 `toolsInclude` 永远通过，因为它没有要求任何一步。

这些断言抓的是 harness、工具和脚本组成的程序：有没有调用不该调用的工具，失败之后有没有停，文本里有没有必须出现的 id。它们抓不住"这段总结写得优不优雅"。那是下一节的事，而且不该拿来替代这里能写死的检查。能用 `includes` 写的，就不要问另一个模型。问模型要花钱，还会抖。

## 一个失败不要挡住后面的

`runEval` 按顺序跑完每一个用例。一个抛了，这条的原因是 `运行抛出了错误：${message}`，继续下一个。示例的输出是：

```text
坏了 运行抛出了错误：超时
好的 tools add,search
passed 1
```

停在第一个失败上，你修一个就冒出一个，也看不到同一次改动打坏了几条。评测和单元测试在这件事上一样：失败信息要能一起看。

一条用例可以同时有多条原因。文本既不等于期望，又不包含某一段，工具序列也不对，记录长度还不同。原因里带上期望和实际：

```text
文本不等于预期：期望 "期望"，实际 "实际"
工具序列不等于预期：期望 add,search，实际 search,search
记录长度不同：期望 2 步，实际 1 步
```

记录长度一样、某一步不一样时，说出下标：`记录第 0 步不符合预期`。下标从 0 开始，和数组一样。只说"不一样"，你还得自己去对。`JSON.stringify` 包住文本，是为了让空格和引号看得见。

用例的 `run` 由调用方提供。它可能是一段写死的轨迹，也可能是 `createAgent` 加 `createScriptedModel` 跑出来的结果。评测函数不关心模型从哪来，只关心结果的形状：`text`、`tools`、`transcript`。同一套断言因此既能锁住脚本，也能在你接上真正的模型时复用。

真正的模型不稳定。断言就要从"等于"放宽到"包含"，并且准备好偶尔失败。那是下一节容忍度要处理的波动，不是这一节把断言写松。CI 里不调用真正的模型。演示程序在设置了 `OPENAI_API_KEY` 和 `OPENAI_MODEL` 时才会连出去，评测默认仍然走假的轨迹。

## 一条用例上的五条原因

练习里有一条故意全错的用例。期望文本是 `期望`，还要包含 `没有这段`；工具序列要是 `add,search`，并且按顺序包含 `search` 然后 `add`；记录要有两步。实际文本是 `实际`，工具是 `search,search`，记录只有一步。`runEval` 应该一次给出：

```text
文本不等于预期：期望 "期望"，实际 "实际"
文本没有包含 "没有这段"
工具序列不等于预期：期望 add,search，实际 search,search
工具序列没有按顺序包含 search → add，实际 search,search
记录长度不同：期望 2 步，实际 1 步
```

`search,search` 不含"先 search 再 add"：第二个 `search` 对不上接下来要的 `add`。子序列不是"每个都出现过就行"，顺序也要在。实现如果遇到第一条原因就 `return`，后面四条消失，这条测试对不上。

另一条用例抛 `模型超时`，后面还有一条能过的。`passed` 是 1，失败列表里只有抛错的那条。`runEval` 自己再抛一次，调用方一个结果都拿不到。

## 黄金轨迹锁的是行为，不是文案的每一个字

`transcript` 把整段都钉死。适合"这个练习的参考运行不能变"。不适合还在改提示的阶段：你改一个标点，全部用例红，红的原因和你要看的退步无关。那时用 `textIncludes` 和 `toolsInclude`，把不能变的事实钉住，把可以说得不一样的话放开。

轨迹里的工具名是暴露给模型的名字。接了 MCP 之后，那是 `notes__add_note`，不是服务器内部的 `add_note`。黄金轨迹如果写了内部名字，前缀一加就全红，红的不是行为变了，是你钉错了层次。

记录比较看三个字段：`role`、`text`、`tools`。长度相同、文本也相同、只是这一步的工具名列表空了，原因是 `记录第 0 步不符合预期`，而不是"文本不对"。先报文本会让人去改回答，真正变的是轨迹。分开报，才知道该看哪一层。

## 停下来想一想

1. 一个用例抛了"模型超时"，后面还有一个本来能过的用例。`passed` 应该是几？如果实现在第一个 `throw` 时把整个 `runEval` 抛出去，你失去了什么信息？
2. 假模型的脚本多了一次 `list_notes`。该用 `tools` 还是 `toolsInclude` 来抓住它？接上会自己决定步数的真模型呢？

空的 `toolsInclude` 不约束任何一步，所以永远通过。把它当成"不允许任何工具"是读反了；那是 `tools: []`。完整序列和子序列的差别就在这一对名字上。写用例时先决定你要钉死的是"恰好这些"，还是"至少这些"。

假模型多叫了一次工具，用 `tools` 能抓住，因为次数也要一致。真模型自己决定要不要多看一眼文件，用 `tools` 会把正常的多看一次判成退步。那种用例改成 `toolsInclude`，只要求关键的名字按顺序出现。两种都写在同一个 `expect` 里也可以：既要求完整序列，又要求其中一段子序列。练习里那条全错的用例就是这样，五条原因一起出来。只实现了其中一种断言，长度对不上。

原因字符串是规格的一部分，不是给人看的随口一句。练习把整段数组 `toEqual`。改一个标点、少一条、多一条，都会红。这比 `toContain` 严，也是故意的：评测的输出会被别的程序读，文案一飘，上层的回归比较就对不上。

用例名字会原样出现在 `failed` 里。两个用例同名，报告里分不清是哪一条。练习没禁止重名，调用方自己保证名字唯一即可，不要在 `runEval` 里再抛一次把整批结果丢掉。名字只用于报告，不参与断言。

`passed` 只数一条原因都没有的用例。有原因的进 `failed`，不重复计入 `passed`。

## 小结

- 能用文本、工具序列、记录说清楚的，就不要交给另一个模型
- 全部用例都要跑完。抛错是这一条的失败原因，可以和别的断言失败同时存在
- 失败信息里带期望和实际。记录要说出是第几步
- 评测函数不绑定某一种模型。CI 用假轨迹；真模型要放宽断言，并接受波动

`run` 抛出的如果不是 `Error`，原因里用 `String(error)`。只读 `error.message` 会在抛字符串的时候再炸一次，整次评测又变成未处理的拒绝。练习里抛的是 `Error`，这条分支留给不是 `Error` 的值。
