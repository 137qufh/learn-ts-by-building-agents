# 7.6 记忆：折叠和长期存储

> 这一节要解决的问题：上下文窗口装不下整段对话，可是随手删掉一条工具结果，下一次请求会被接口拒绝。对话结束之后，下一回还想用上"用户要低脂奶"，这段话又该放在哪？

示例代码：[examples/06-memory.ts](examples/06-memory.ts)

## 短期：折叠，但按块

第 6 章的 `fitToBudget` 按轮次丢掉旧消息，解决的是"这次请求太长"。有时你不是丢掉，而是换成一段摘要：旧的过程不重要，结论要留下。

摘要有一条硬约束。一条带着 `tool_calls` 的 assistant 消息，后面必须有对应的 tool 消息。只留下工具结果、或只留下调用，下一次请求不合法。所以折叠的单位是 **块**：

- 第一条 system 永远留下，不进摘要，也不占 `keep` 的名额
- 带工具调用的 assistant 和紧跟着的 tool 消息是一块
- 从末尾留块，直到留下的消息条数达到 `keep`。一块有两条，而 `keep` 只要一条，就整块留下

示例里 `keep` 的效果是：昨天的用户问题被折成一句，加法和它的结果还在。`covered` 是 1。调用 `summarize` 之前，先用 6.5 节的 `repairHistory` 把被中断的记录补齐。这一节假定记录已经是完整的。

摘要插回去的是一条 user 消息，开头写明"这是更早对话的摘要，不是新的问题"。放成 system 会和真正的系统提示缠在一起；放成普通用户问题，模型会把它当成新的指令。

## 长期：这次运行之外

窗口里的消息随 `run` 结束就只存在于调用方保存的数组里。下一回、另一个进程，默认什么都不记得。长期记忆是一个单独的存储：`add`、`list`、`search`。进程内的数组够把接口写对；换成文件或数据库时，调用方不用改。

`search` 不要把空查询当成"返回全部"。模型会调用 `search("")`。全部用 `list()`，那是显式的。空文本不让写入。

中文没有空格。按空格分词的话，"牛奶"永远撞不上"买牛奶"。这里的规则是：词，再加上长度超过两个字的词的相邻二字。"牛奶"是一个二字词；"买牛奶"会多出"买牛"和"牛奶"。查询"牛奶"就能命中。这不是分词器，人名和专业词会切错。它只保证离线、确定、对这种包含关系有用。

`list` 和 `add` 返回副本。调用方改返回值，不该改到库里的那一条。这又是"交出去的对象会被人留着"的问题。

## 小结

- 折叠以块为单位。system 留下，工具调用和它的结果不拆开
- 摘要是一条标明身份的 user 消息，不是新的系统提示
- 长期记忆是运行之外的存储。空查询返回空，想看全部用 `list`
- 没有分词器时用词加二字片段，让"牛奶"能命中"买牛奶"
