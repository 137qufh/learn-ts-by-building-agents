# 7.6 记忆：折叠和长期存储

> 这一节要解决的问题：上下文窗口装不下整段对话，可是随手删掉一条工具结果，下一次请求会被接口拒绝。对话结束之后，下一回还想用上"用户要低脂奶"，这段话又该放在哪？

示例代码：[examples/06-memory.ts](examples/06-memory.ts)

## 短期记忆已经在记录里

第 6 章的 `messages` 就是短期记忆：模型下一步能看见的全部。`fitToBudget` 在太长的时候按轮次丢掉旧消息，解决的是"这一次请求塞不进窗口"。有时旧的过程不重要，结论要留下。丢掉和折成一段摘要，是两种不同的压缩。

摘要有一条硬约束，来自接口，不是来自偏好。一条带着 `tool_calls` 的 assistant 消息，后面必须有对应的 `tool` 消息，用 `tool_call_id` 对上。只留下结果、或只留下调用，下一次请求不合法。所以折叠的单位是 **块**，不是一条一条的消息：

```ts
if (message.role === "assistant" && message.tool_calls?.length) {
  const group = [message];
  while (下一条是 tool) group.push(下一条);
}
```

第一条如果是 `system`，永远留下，不进摘要，也不占 `keep` 的名额。系统提示是配置，不是对话。其余的从末尾留块，直到留下的消息条数 **至少** 是 `keep`。一块里有三条（一次调用加两条结果），而 `keep` 只要两条，就整块留下。宁可多留，也不要从块的中间切开。

示例的四条是：system、一条旧的用户问题、一次工具调用、一条结果。`keep` 只够留下末尾那一块时，打印是：

```text
covered 1
roles system,user,assistant,tool
```

中间那个 `user` 不是原来的问题，是插进去的摘要。原来的用户问题在 `covered` 里。调用和结果还在。

`keep` 为 0：除了 system，全部折叠。`keep` 不是非负整数就抛 `RangeError`，不要把 `1.5` 收成 1。没有可折叠的消息时 `covered` 是 0，并且 **不调用** `summarize`。摘要函数可能很贵，没有东西可摘要还去调用，是白花钱，测试也没法断言"它没跑"。

## 把 keep 为 2 的五条走一遍

练习里有这样一列，用来防止"只粘住第一条 tool 结果"：

1. user `算两个`
2. assistant，带着工具调用
3. tool `1`
4. tool `2`
5. assistant `好`

分块之后是三块：`[user]`、`[assistant, tool, tool]`、`[assistant 好]`。`keep` 是 2。从末尾数：最后一块只有 1 条，不够，再拿前面那一整块，一共 4 条，已经超过 2，停。用户那条被折掉，`covered` 是 1。留下的角色是 `user`（摘要）、`assistant`、`tool`、`tool`、`assistant`。

如果循环只 `push` 第一条 tool 就停，第 4 条会变成自己的一块。`keep` 为 2 时留下的是最后的 tool 加上最后的 assistant，调用本身被折进摘要，记录里出现一条没有调用的 tool。下一次请求不合法。测试要的就是那两个 `tool` 都还在。

## 摘要插回去时，它是谁

插回去的是一条 user 消息：

```ts
{ role: "user", content: `以下是更早对话的摘要，不是新的问题：\n${summary}` }
```

放成 system，会和真正的系统提示缠在一起，模型分不清哪句是规矩、哪句是过去的对话。放成普通的用户问题，模型会把它当成新的指令去执行。开头那句就是在消除这个歧义。

折叠之前先用 6.5 节的 `repairHistory`。被中断的记录里可能有没有结果的调用。这一节的分块假定记录已经是完整的：调用和结果相邻。在一笔缺了结果的记录上做摘要，会把一个残缺的调用折进摘要，或者把一条孤儿结果单独留下，下一次请求照样不合法。先修，再折。

## 长期记忆是另一次运行还在的东西

窗口里的消息随 `run` 结束，只存在于调用方保存的数组里。下一回、另一个进程，默认什么都不记得。长期记忆是一个单独的存储，三个方法：`add`、`list`、`search`。进程内的数组够把接口写对；换成文件或数据库时，调用这三个方法的代码不用改。

几条和窗口不一样的规则：

- 空文本不让写入。`trim()` 之后是空的就抛。空白不是一条记忆
- `search("")` 返回 `[]`，不是全部。模型会调用空查询。想看全部用 `list()`，那是显式的
- `add` 和 `list` 返回副本。调用方改返回值的 `text`，库里的那条不变。交出去的对象会被人留着，6.1 节和 7.5 节已经各踩过一次
- id 是 `m1`、`m2`……时间由调用方传入。测试才能固定"哪条更新"

排序：重叠的片段越多越靠前；一样多，`createdAt` 新的在前；还一样，id 字典序。最后一条是为了稳定。时间相同的两条如果顺序看心情，回归测试会自己抖。

## 没有空格的语言

按空格分词，"牛奶"永远撞不上"买牛奶"。这里的规则是：先取出连续的字母或数字（`\p{L}` 和 `\p{N}`），再对 **长过两个字** 的词补上相邻的二字。"买牛奶"会得到词本身，加上"买牛"和"牛奶"。查询"牛奶"就能命中。二字词本身不再把同一个片段算两次。

示例的 `found 买牛奶` 就是这条规则，不是 `includes`。

这不是分词器。人名、专业词会被从中间切开，不相干的二字也会碰巧重叠。它只保证离线、确定、对这种包含关系有用。要语义（"牛奶"对上"乳制品"），是下一节的向量，而且默认那一版向量也做不到，要换真正的 embedding 模型。

时间相同的两条都含"牛奶"时，id 是 `m1` 然后 `m2`。比较器少了 id 这一级，顺序就只剩"谁先写进数组"，听起来一样，换一种存储就变了。测试把 `createdAt` 都设成 5，就是为了把这一级单独露出来。

空查询返回空数组，`limit` 为 0 也返回空数组。负数抛 `RangeError`。这三件事和"没找到"是不同的：没找到是有查询、重叠数是 0；空查询是根本没有片段可对。

## 停下来想一想

1. `keep` 是 1，末尾是"一次工具调用加两条结果"再加一条普通 assistant。会留下哪几条？为什么不能只留最后那条 assistant 和其中一条 tool？
2. 空查询如果返回全部记忆，模型一次 `search("")` 会把库里所有文本送回上下文。这和"记忆是为了少放进提示"哪一条相反？

## 小结

- 折叠以块为单位。system 留下；带着 `tool_calls` 的 assistant 和紧跟着的 tool 消息不拆开
- 没有东西可折时不调用 `summarize`。摘要是一条标明身份的 user 消息
- 先 `repairHistory`，再折叠
- 长期记忆是运行之外的存储。空查询返回空；`list` 和 `add` 交出去的是副本
- 没有分词器时用词加二字片段，让"牛奶"能命中"买牛奶"。这不是语义
